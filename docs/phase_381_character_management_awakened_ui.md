# Phase 381：角色管理觉醒式界面

## 参考意图

项目所有者要求把进入游戏后右下角的“状态”入口改为“角色”，并以提供的成熟产品截图
作为信息层级和交互节奏参考，重做角色管理页。参考重点是：全屏沉浸式木石框架、人物与
装备的主视觉、右侧分页、明确的属性反馈、先预览再确认的加点操作，以及可筛选的骑乘
资格总览。

Beastbound 只复用这些经过验证的布局与交互原则，不复制参考游戏的像素、美术、宠物
名字、数值、商标或原始资源。页面继续使用项目现有原创人物、宠物大头照、装备图标和
共用 UI 皮肤；数据和功能也只展示 Beastbound 已真实存在的系统。

## Beastbound 原创边界

本阶段不为了“看起来像参考图”伪造尚未存在的玩法或数值：

- 不显示虚构的称号、家族、气力、怒气、人物战力或“启动特权”；
- 不硬编码参考图中的暴击、闪避、反击、命中等固定百分比；只有项目权威档案能够计算
  或提供的字段才允许进入玩家界面；
- 不伪造骑宠、骑证、种族条目或“未激活”收藏图鉴；骑证页当前只投影三种真实可骑
  形态；
- 不把客户端临时展示值写回存档，也不让客户端绕过服务端权威分配人物属性点；
- 不把 QA、资源路径、raw code、schema、接口名、测试状态或录屏说明画进玩家页面。

当前三个真实可骑形态为：

| 形态 ID | 玩家形态 | 当前资格来源 |
| --- | --- | --- |
| `bui_novice_sprout_earth5_wind5` | 芽耳布伊骑乘形态 | 真实骑宠资格证 `ride_bui_novice_sprout` |
| `novice_tiger_mount` | 新手老虎骑乘形态 | 项目既有免证骑乘合同 |
| `thunder_dragon_mount` | 雷龙骑乘形态 | 项目既有免证骑乘合同 |

后续只有在宠物目录、骑乘资产、资格规则和服务端档案都真实存在后，才可自然增加骑证
卡片。页面数量不能反向驱动虚构数据。

## 入口与全屏合同

- 世界右下角原“状态”按钮改为“角色”，左键打开全屏角色管理页；右键不能成为必要
  操作；
- 页面固定按 PC 首发基准 `1280×720` 构建，顶部显示“角色”和关闭按钮，关闭后返回
  原世界状态；
- 右侧提供 `属性 / 加点 / 骑证` 三个纵向页签；切换页签不得重复读取存档或发起网络
  请求；
- 弹窗打开时阻止世界点击穿透；关闭、切页、滚动、加减和卡片选择均须保持边界内可见；
- 继续复用已有角色面板注册与世界菜单关闭规则，不另造一个脱离正常游戏入口的演示页。

## 属性页

属性页承担“看清当前角色”的职责：

- 左侧完整显示项目现有九个装备槽；空槽保持明确空态，已装备槽使用真实实例、品质和
  图标；点击装备继续进入既有背包／装备详情与对比流程；
- 中间显示当前角色名字、原创全身形象和真实出战宠／骑乘宠卡片，不使用占位人物冒充
  当前外观；
- 右侧只投影真实等级、经验、生命、四维、装备加成、剩余属性点和人物元素；
- 地、水、火、风继续使用项目统一的绿、蓝、红、黄语义，元素总量与组合来自权威档案；
- 基础值、装备加成和最终显示值必须分层计算，不能把装备加成重复计入基础四维，也不能
  在不同属性间串值。

## 加点页

加点页采用“客户端草稿、一次确认、服务端原子结算”的合同：

1. 玩家点击四维的 `+ / -` 只修改本次页面草稿，不立即改档、不逐点请求服务端；
2. 草稿持续显示各项预计结果和分配后的剩余点数，减号不能低于本次已加数量，加号不能
   超过真实剩余属性点；
3. “清空本次”只清除尚未提交的草稿，不返还历史已分配属性点；
4. “确认加点”一次提交 `player_stat_allocate_batch`，请求只包含
   `maxHp / attack / defense / quick` 四个允许字段的非负整数；
5. 服务端验证字段集合、整数类型、非负、非零总量和可用点数。全部合法时一次更新人物
   属性并只推进一次 revision；任一字段非法或总量越界时整批拒绝，档案不得部分变化；
6. 请求进行中禁止重复确认；成功后使用服务端返回的最新 profile 刷新页面，失败时保留
   玩家可修正的草稿并显示玩家可理解的通用提示。

本阶段没有“洗点”功能。历史属性重置涉及价格、次数、可返还范围和在线权威规则，项目
所有者尚未决定；因此不能把参考图中的“洗点”按钮做成免费重置，也不能用“清空本次”
暗中代替历史洗点。关闭页面时未提交草稿直接丢弃。

## 骑证页

“骑证”是 Beastbound 的骑乘资格浏览页，不是虚构宠物图鉴：

- 首屏提供“全部”和真实种族筛选；筛选只作用于已投影的骑乘形态，不产生新条目；
- 卡片使用共享宠物大头照，显示真实形态名、所属族和当前是否具备骑乘资格；
- 资格状态来自真实骑证库存和既有免证骑乘合同，客户端不能凭卡片状态授予资格；
- 当前只有三种真实可骑形态，因此页面宁可保持三张可信卡片，也不照搬参考图填满九格；
- 未来新增条目必须同时满足宠物／坐骑资产、目录、资格来源、权威档案与验证门，不能只
  补一张 UI 图片。

## 验证门禁

完成本阶段必须至少通过以下聚焦验证：

- Presenter／模型检查：九个装备槽、真实人物字段、装备加成分层、人物元素、出战／骑乘
  宠物及恰好三个真实骑乘形态的确定性投影；
- 面板交互检查：三页签、关闭、装备入口、加点 `+ / -`、清空草稿、确认、骑乘筛选与
  卡片均可通过左键操作，且所有控件在 `1280×720` 安全边界内；
- 服务端测试：整批合法加点、点数不足、额外字段、负数、小数、字符串数值、全零请求、
  并发／revision 行为和失败不部分落档；
- Godot 全项目 parse，以及既有角色状态、人物属性点、骑乘、面板注册和人物运行时外观
  回归门禁；
- `git diff --check` 与所改 JSON／Node 文件的语法解析检查。

角色页属于玩家高频世界菜单，实装后还必须记录打开前后空闲性能和真实跨帧移动性能。
面板关闭后的世界移动应稳定恢复，页面刷新不得在 `_process`、`_draw` 或 UI 签名热路径
反复执行完整 profile 归一化、全背包扫描或网络请求。

## 视觉与录像验收

- 使用真实 `res://scenes/Main.tscn`，从世界右下角左键点击“角色”进入，而不是只录独立
  预览场景；
- 以 `1280×720 / 30 FPS / 1.00×` 连续展示属性页、九装备槽、人物与宠物、加点草稿、
  原子确认、全部骑证、种族筛选、关闭并恢复世界移动；
- 录像使用隔离 profile 和本地 QA 环境，不覆盖真实玩家存档，不连接共享／生产后端，不
  消耗真实物品或货币；
- 将项目所有者四张参考截图分别与同状态实机帧放入同一个 Design QA 比较输入，修复所有
  P0/P1/P2 后，`design-qa.md` 必须以 `final result: passed` 结束；
- 工程自动检查不能代替项目所有者的画面验收。最终交付必须给出可直接点击播放的 1×
  视频；只有项目所有者明确通过后，才算完成主观视觉验收。

- 不为凑版面添加假装备、假属性、假骑宠或假资格证；
- 不改变宠物骑乘、美术终端形态、人物元素、装备结算或角色创建的既有产品规则；
- 不复制参考游戏的原始图像、人物、宠物或数值；
