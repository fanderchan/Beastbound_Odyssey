## 静止增量诊断

先用原生脚本分析器取得二层网格／美术／美术／网格四段有效样本，每段 361 个观察帧均实际绘制，零失焦／零不可绘制。当前相机缓存没有每帧重新求解，遮挡也没有每帧遍历全部物件。分析器本身带开销，其函数时间只用于定位，不能作为性能门或 CPU 结论。

随后使用预分配数组和同帧开始／结束节点记录所有 Node 回调区段，关闭详细 `--perf-probe` 与脚本分析器。每种条件四段，各 480 帧，均持续前台实际绘制。下表是每种渲染路径两段均值的平均，单位 ms；属于诊断，不替代 Phase 579 的完整三重复性能矩阵。

| 条件 | 网格 | 美术 | 增量 |
| --- | ---: | ---: | ---: |
| 正常时钟、普通运行同步设置 | 0.348051 | 0.463951 | 0.115900 |
| 固定步长参数、保留 Main 的同步设置 | 0.249248 | 0.288541 | 0.039293 |
| 固定步长、明确关闭运行时垂直同步 | 0.147017 | 0.297165 | 0.150148 |

第二组的命令行 `--disable-vsync` 会被 Main 的普通启动配置覆盖，且该组没有记录运行时同步状态，不能声称与正式性能测试同条件。第三组在 Main 初始化后明确关闭同步，并逐段确认 `vsyncMode=0`；480 帧实际耗时 `3.279–3.683s`，不是正常 60 FPS。正常时钟及第二组约为 30 个实际绘制帧每秒。

第三组仍有约 `0.150ms` 增量，因此没有证据把既有失败归咎于详细计时，也不能用第二组较小的数字宣布通过。正常时钟的两段美术均值为 `0.526263 / 0.401640ms`，波动也需保留。

另外，在 scratch 中比较遮挡查询的反射调用和带类型直接调用：七次重复、每次两万次调用，中位数分别 `1.29345 / 1.29335µs`，无有意义收益，未采用。没有将这种微测量解释为帧耗时改善。

诊断数据见 [汇总](../.run/phase580-diagnostics/summary.json)、[当前脚本分析](../.run/phase580-native-script-current/comparison-summary.json)、[明确同步设置的区段采样](../.run/phase580-uninstrumented-fixed-no-vsync/report.json)。既有正式静止增量门仍为 `≤0.100ms`，Phase 579 的整体 **FAIL** 保持有效，没有重新运行无变化的完整矩阵或覆盖正式 bundle。
