## 正常设置下的 CPU 局部证据

本轮最初复用的早期 scratch 入口缺少正式准备页已有的单次激活请求，首次运行未满足前台条件，未取得 CPU 样本。对齐这项启动行为后，同一窗口开始网格／美术／美术／网格四段正常运行对照：不使用固定步长、详细探针或脚本分析器，保留 `maxFps=30 / vsyncMode=1`，不补绘、不在采样期间激活窗口。每段先要求连续 8 秒且至少 200 个实际绘制帧，再观察 20 秒。

通过外部 `ps` 累计进程 CPU 时间差除以单调墙钟时间，得到下列诊断结果。前三段各 600 个观察帧和实际绘制帧、零失焦／零不可绘制；第四段出现 434 帧失焦，整批按设计失败，没有合并成完整对照或 PASS。

## 准备页现在能说明为什么没开始

`map_performance_batch.gd` 原先只返回 `foreground_unavailable`，把未收到开始点击、失焦、不可绘制和稳定绘制不足混在一起。现在只在准备阶段统计独立阻断帧数，并在超时时输出：最后的开始请求／焦点／可绘制／渲染循环状态、观察与实际绘制帧数、最长稳定时段、稳定绘制进度及 Main 数量。多个条件同时失败时全部保留，不猜测操作系统原因。

120 秒超时、真实开始点击、至少 1 秒稳定且 30 帧绘制的原门槛不变。诊断不进入游戏 UI 或测量阶段，也不会自动确认开始。

原生负例刻意不发送开始点击，`120009ms` 后正常拒绝：`7196` 个观察帧、`7195` 个绘制帧，全部观察均未请求开始，仅 1 帧失焦；最后窗口有焦点且可绘制。全程 Main 数为零，没有生成采样开始记录，见 [准备页负例](../.run/phase593-readiness-diagnostic/report.json)。这证明“没有开始”不能直接解释为“窗口一直没有焦点”。

本阶段交互尝试另保留 5 次原始 Computer Use 调用／1 张图片，准备按钮点击返回 `noWindowsAvailable`；CPU 等待页的 Raise 没有令首次对照开始。原始记录 SHA-256 为 `1d341b6d734fc329ec77694729d5ad68c514f58aae5619ee5c2e7a6df08f522d`，见 [调用索引](../.run/phase593-computer-use/index.json)。系统只读查询为 `IOConsoleLocked=false`，没有据此宣称窗口工具恢复正常或归因于锁屏。
